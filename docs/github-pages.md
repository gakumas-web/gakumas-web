# GitHub Pages 同源图片部署

站点通过手动触发「发布 GitHub Pages」工作流发布。工作流从 `resources/pages-source.json` 固定的 Release 下载内容包，验证大小、SHA-256 和内容合同，再下载其中的基础图片分段与增量对象；每个下载同样核对大小与 SHA-256。随后在构建中生成用途小包与长边不超过 384px 的卡图缩略图，缩略图单独记录哈希。只上传构建后的 `dist/`。

资源文件只进入部署产物，不进入 Git 历史。浏览器从与页面相同的来源下载用途小包，原图片索引、内容清单和原图哈希保持不变。构建生成的分发规划包含基础界面、回忆、目录、成就及完整卡图分类；偶像卡与支援卡分别生成独立原图包和缩略图包，装扮专用卡面依据公共目录的主题分别生成两类包。装扮与基础偶像卡共用的卡面优先归入偶像卡包，同一对象不重复打包。每个功能包最多约 4 MiB 的图片字节，基础界面包最多约 2 MiB。构建生成的地址映射使用相对路径，兼容 Pages 仓库子目录；原有本机图片缓存和分段恢复继续生效。默认 `tools/build.py` 仍不启用图片。

页面只请求实际渲染图片所在的包；进入偶像卡页不会因同包混装而下载支援卡或装扮专用卡面，反向同理。装扮页选择主题后只新增该主题所需的包及共用卡面包；选择全部主题仍可能请求多个主题。切页提高新需求优先级，不强制中断此前已开始的下载。原图仍在完整展示或「准备完整图片」时请求。

首次部署前在仓库 Settings → Pages 中选择 GitHub Actions。工作流使用平台提供的临时令牌，不需要个人 PAT Secret。Pages 的发布目录含完整内容和图片副本，须保持在 1 GB 内；每月 100 GB 为平台软流量限制。

## 更新

先生成并发布通过当前合同校验的内容包，然后更新 `resources/pages-source.json` 中固定的版本、下载 URL、字节数和 SHA-256，再重新运行工作流。不得使用 `latest` 地址。上游图片分段也必须已发布且能由 Actions 下载。

同源部署的图片副本与程序一起构建，因此更新图片来源时须重新部署整套站点，不单独替换频道或安装未镜像的新内容。发布失败时不切换线上站点。上游 Release 更新不会自动触发本仓库部署。

本地复现：

```sh
python3 -m pip install -r requirements-build.txt
python3 -B tools/build_pages.py --output local/pages-test/dist
python3 -B -m http.server 8080 --bind 127.0.0.1 --directory local/pages-test
```

打开 `http://127.0.0.1:8080/dist/`，可验证子目录下的内容与图片下载。库存仍由浏览器本地处理，不进入 Pages、Release 或部署流程。

## 加载与兼容

后台准备状态显示在「数据」按钮：进行中使用小型指示，失败保留警示入口，自动补图完成后恢复普通按钮，不在正文常驻成功提示。资料尚不可用时，内容区保留准备提示及失败重试，账号导入不受影响。用户主动准备完整图片时，按已准备好的对象展示进度；关闭数据窗口后完成会短暂提示，失败和停止不显示成功。下载字节只作为会话统计，下载完成但仍在处理时不报告整体完成。

公共资料完成校验后立即可用，图片单独运行。无账号的欢迎页只准备基础界面图片；进入页面后按实际渲染需求请求对应小包。列表使用生成的缩略图，完整卡图在打开详情或选择「准备完整图片」时获取。最多两个包在途，待解包的包也占下载槽；解包与保存串行，不把全套包积压进内存。

成功分段和原图对象按哈希复用。停止只保留已完成项，不承诺从包内中断字节继续。重试重新获取失败包，下载、校验、解包与保存分别反馈。图片缓存完成不表示程序支持断网启动。

本次迁移保留当前来源版本的原始分段，供旧页面继续下载；新页面只请求用途包。保留范围不累积历代版本，报告将兼容分段与新流程下载量分开统计。`build-report.json` 和 Actions 摘要提供分类体积与首访图片预算，已有账号的实际首屏量随当前视图变化。

加载诊断只包含公开内容版本、阶段时间、对象哈希、字节数与错误类型；不包含账号、库存、认证信息或请求正文。资料与图片面板中的缓存清理只清公共图片数据库，不清账号及笔记。

旧用途包不承诺跨部署永久保留。仍打开的旧页面首次访问未缓存图片时，如旧包已移除，会显示缺文件提示并展开「刷新以更新资源」入口；账号导入进行中禁止刷新。刷新读取新版程序与资料，账号继续由同源 IndexedDB 恢复。`tests/browser_review_regressions.py` 使用两个图片及用途包哈希不同的真实构建验证此路径，不以原始兼容附件仍可访问代替跨版本验收。


## 图片构建缓存

Pages 构建可复用已经校验的原始分段、增量对象、用途包及缩略图规划。缓存键包含图片索引 SHA-256、目录生成的图片主题与页签分组映射 SHA-256、生成与校验脚本、构建依赖锁、Python／Pillow／WebP／zlib 版本及运行平台；不包含前端提交号，因此只改 HTML、JS 或 CSS 不会重新处理图片。公共资料变化但图片索引与图片分组映射均未变时同样可以命中。

恢复后先核对输入身份、来源图片身份、缩略图映射、用途分组、文件集合及每个文件的大小和 SHA-256，再复制到新构建。图片配置仍由当前代码生成，程序始终从当前提交构建。冷、暖构建的发布文件应逐字节一致，仅构建报告的状态和耗时不同。

缓存缺失时正常生成；损坏时保留无效目录并从固定来源重新生成。缓存写入失败不阻止已经校验的站点构建。Actions 只恢复完全相同输入身份前缀下的缓存，重建成功后使用新的运行号保存，避免损坏的不可覆盖缓存反复被优先使用；有效命中不重复保存整套图片。

`dist/build-report.json` 的 `image_cache.status` 为 `hit`、`miss`、`invalid`、`write-failed` 或 `disabled`，并记录缓存键与 `build_seconds`。是否真正命中以构建器校验结果为准，不以 Actions 的前缀匹配结果代替。Actions 缓存可能被回收，回收后仍能完整重建；当前未将它作为永久制品来源。

本地启用：

```sh
python3 -B tools/build_pages.py --image-cache local/pages-image-cache --output local/pages-cache-test/dist
```

手动工作流的 `publish` 默认开启；关闭时只执行检查、构建及缓存读写，并保存构建报告，不进入 Pages 部署任务。可以用连续两次关闭发布的运行测量冷构建与缓存命中耗时。

### 云端冷暖构建对照

同一图片输入及生成工具链的两次构建验证结果：

| 指标 | 冷构建 | 缓存命中 |
| --- | ---: | ---: |
| 构建器耗时 | 388.764 秒 | 2.575 秒 |
| Actions 缓存恢复步骤 | 1 秒（未命中） | 4 秒 |
| 构建验证任务总耗时 | 474 秒 | 73 秒 |

冷暖两轮的 `release.json` 完全一致，所列 164 个文件的哈希全部相同；有效命中没有重复保存缓存。这是单次云端对照，任务总耗时包含检查、依赖安装及构建，但两次均关闭发布，不包含 Pages 制品上传和站点切换。

证据：[冷构建](https://github.com/gakumas-web/gakumas-web/actions/runs/37465908670)、[缓存命中](https://github.com/gakumas-web/gakumas-web/actions/runs/37466983442)。构建报告作为各运行的 `pages-build-report` 制品保存。

## 发布身份与冒烟记录

`release.json` 可包含 `source_commit` 和 `build_run_id`，分别来自显式的 `GITHUB_SHA` 与 `GITHUB_RUN_ID` 构建环境。仅接受完整提交哈希及数字运行号；缺少有效提交身份时不写这些字段，也不读取本地 Git HEAD 推断。它们不参与图片缓存身份。

在对应源码版本下，可用 `tools/verify_site.py` 核对实际入口、关键程序文件哈希、基础图片缓存复用、缩略图／原图分级及手机布局。该工具创建新的浏览器上下文，不读取已有账号；需要构建测试环境的 Playwright 与 Chromium。使用 `--expected-commit` 可要求清单明确匹配目标提交。下例的 `DEPLOY_COMMIT` 应先设置为待核验的完整提交哈希。

```sh
python3 -B tools/verify_site.py --url https://gakumas-web.github.io/gakumas-web/ --expected-commit "$DEPLOY_COMMIT" --output local/site-verification.json
```

报告记录采样时间、入口、原始清单 SHA-256、程序版本、声明的源提交和构建运行号、浏览器版本，以及首次访问和同上下文重载场景。旧清单没有来源字段时保留未知，不能单凭相同程序版本名认定为同次部署。本地入口产生的报告只证明本地构建，不代表线上发布。
