# 加载改造验收（2026-10-06）

本轮保留 GitHub Actions → 固定 Release → Pages 的交付路线，程序版本为 0.6.0-preview。业务内容和原图片字节没有升级；用途包是部署分发规划，缩略图另有内容哈希，不改写来源索引。

## 可复现的行为检查

- 公共资料就绪不等待图片：浏览器拦住首个图片响应时，资料版本已激活，目录导入入口可操作。
- 两条下载任务、单个解包／保存任务；已下载而未处理的包仍占槽，第三个任务不会无限积压。
- 图片按成功分段局部显示；有效缓存复用，损坏缓存修复，失败重试保留成功项。
- 停止后可以重试；存储空间不足会停止新增下载。公共图片清理不删除合成账号及库存。
- 主入口加载失败时显示独立启动错误及刷新入口；资源状态通过同一状态源驱动，进度更新不重建列表。
- 仓库子路径、375px 小屏和日文状态文案通过；Ending 奖励语义未改变。
- 使用真实资源与生产插图组件，依次观察到 `core` → `catalog-thumbnails` → `artwork-other` 请求。列表图片为 384×384，进入完整展示后为 2048×2048；没有提前下载对应完整卡图。

相关检查为 `tests/image-manager.test.mjs`、`tests/test_image_plan.py`、`tests/browser_image_delivery.py`、`tests/browser_content_updates.py`。浏览器只使用合成账号或空账号上下文，验证没有账号正文上传。

## 本机对比基线

改造前程序来自 `7f225a8`，改造后使用本轮功能构建。两者使用相同的 `20261006.pages-test.1` 内容和原图，来自同一台本机 HTTP 静态服务；无网络或 CPU 节流，Chromium 149.0.7827.55。构建工具生成程序，测试装配使用已核验的同源附件；没有替换运行时下载器或存储实现。它衡量应用等待关系，不是 Pages 公网或大陆三网测速。

每种情况采用三个样本的中位数。冷启动使用新的隔离浏览器上下文，没有 HTTP／IndexedDB 缓存或 Service Worker；缓存启动在同一上下文重载。首轮基线与独立组件检查短暂重叠，已排除并补测。

| 无账号场景 | 改造前 | 改造后 |
| --- | ---: | ---: |
| 冷启动导入入口可用 | 266 ms | 234 ms |
| 冷启动公共资料就绪 | 9,275 ms | 932 ms |
| 冷启动当前图片任务结束 | 9,287 ms | 1,081 ms |
| 冷启动图片下载 | 7 包，228,564,872 字节 | 1 包，252,575 字节 |
| 缓存启动公共资料就绪 | 46,262 ms | 770 ms |
| 缓存启动当前图片任务结束 | 46,266 ms | 1,856 ms |
| 缓存启动图片下载 | 0 | 0 |

两版的「当前图片任务」范围不同：旧版为整套图库，新版为基础界面所需图片。该差别正是本轮减少首次工作量的目标，不能把它解释为同等总量的吞吐提升。当前功能还未请求的卡图会在查看时加载。

旧版缓存启动仍串行读取、校验全部图片，并让公共资料等待其结束；新版只检查请求到的图片，且不阻塞资料。上述数字不能单独说明每一毫秒花在哈希还是 IndexedDB。诊断中的并行任务时长可能重叠，不可直接相加当作总耗时。

## 体积与后续取舍

本轮基础界面为 140 个图片对象，首包约 247 KiB；679 张完整图生成长边不超过 384px 的缩略图。完整准备包含缩略图，仍约 233 MiB，因此不会默认在欢迎页下载。

迁移期间同时保留本次源版本的原始分段，供之前已经打开的页面完成下载，发布目录约 490 MiB；新页面只请求用途包，不重复下载兼容分段。每次构建以 `build-report.json` 和 Actions 摘要的实际数字为准，并检查最终发布目录不超过 1 GB。

本轮未引入 Worker：已确认的主要等待关系已解除，先保留小包、有界下载和单处理队列。若移动端的阶段计时、长任务记录表明解包仍是瓶颈，再针对测得的计算阶段评估线程迁移。未实现整站断网启动，不作离线使用承诺。

## 源码复审后的修正与验证

针对 `ad7ea01` 的复审补齐以下边界：图片需求全部完成后才报告就绪；缓存检查与已排队任务都接受前台优先级；旧代任务退出、迟到异常与清空后重试分别收敛。移除没有生产读取方的 `initialized` 元数据写入，图片有效性仍以对象哈希和存储事务提交为准。界面捕获图片操作失败，错误出现时展开恢复入口。

缓存检查默认最多同时执行 8 项，图片可用通知在 16 ms 窗口内合并，最后完成时立即发布。140 个有效缓存对象的定向测试将检查峰值从 140 降至 8、通知从 140 次降至本次实测 2 次，下载仍为 0；通知次数会随机器调度变化，不是固定性能承诺。

公共资料的检查、正文读取、校验和保存接入全局面板；读取字节仅统计资料响应正文，不等同网络传输流量。资料仍整套校验并原子激活。Ending 呈现保留未知状态，坏视图偏好只回退显示设置，均不改变奖励数值或账号库存。

诊断保留首次启动记点，同时增加带视图／运行号或图片版本／需求范围的事件；后台分包完成不再直接算当前视图就绪。`cacheCheckMs` 是并行对象检查耗时之和，不能当作墙钟等待时间。上文历史性能表保留原始测量前提，完成记点存在提前报告路径，因此后续性能比较须重采修正后的基线，不能直接沿用旧完成时间宣称提升。

本轮本地验证：

- 60 项相关 Node 测试通过；其中包含将复审探针转为回归测试后的状态、优先级、生命周期与缓存工作量检查。
- 干净源码副本中独立运行 `test_content_install.py` 的 2 项测试通过，不依赖预先运行公开检查创建 `local/`。
- `browser_image_delivery.py` 与 `browser_content_updates.py` 通过，覆盖真实静态构建、IndexedDB、图片重试、子目录及账号保留。
- `browser_review_regressions.py` 覆盖资料请求等待／失败／重试、损坏偏好恢复、Ending 未知态、375px 日文布局，以及两次不同用途包构建之间旧页首次请求原图、404 提示、刷新后账号保留与新版原图解码。浏览器场景使用合成账号，只允许 GET／HEAD，无库存上传。

这些验证均为本地证据，不代表本轮已经发布或重新验证公网性能。

## 后续验收与角色占位

后续优化将图片发布改成增量名称通知，状态通知按 32 ms 合并，完成、取消与配置切换立即刷新；需求完成数增量维护，不再在每次状态读取时扫描全部需求。兼容需要完整 URL 映射的订阅者，公共图片清空时显式撤销对应映射。缓存读取仍保持最多 8 个并发，并逐对象验证字节和哈希。

加载诊断的 `runs` 保存任务开始、结束、耗时及结束原因，视图切换和重试拥有独立记录。A 页迟到完成不能结算 B 页；图片记录注明视图、版本及所需／完整准备范围。字段仅包含公开加载信息。

可确定角色的立绘、偶像卡、装扮、选拔卡面、角色成就和单角色支援卡，在图片缺失或等待时使用对应角色头像。占位头像最多 32px，使用 `object-fit: scale-down`，小于此尺寸的图片也不放大；头像不可用时回到文字占位。原图就绪后只替换图片，不改变业务状态。

Ending 详情提供带状态名称的原生按钮，可通过键盘及触屏打开说明；图库中的徽章保持非交互图片语义，避免嵌套按钮。已验证 360px／390px、根字号 200%、日文布局，以及未知与明确未记录的区分。

后续浏览器回归同时覆盖：非法 JSON／null／数组／未知页签恢复、恢复后导出、导入另一个账号再切回、无新增图片／缩略图／完整图片三态下的库存节点与数值、比较选择和滚动位置保持，以及多标签页共享图片库和版本升级关闭旧连接。真实 IndexedDB 事务中止后，对象与包标记均未部分提交。

**配额验证限制**：本机 Chromium 接受 CDP 的 1 字节配额覆盖，但仍允许提交超过限额的数据，因此不能将该探针视为真实 `QuotaExceededError` 验收。测试记录 `real_quota_error: false`；管理器的配额异常处理由定向故障注入覆盖，真实浏览器事务中止另行通过。不填满用户磁盘来强行触发配额错误。

全量 Node、Python、Docker 构建，以及真实 `managed` 静态入口的六页签、加密备份、清理恢复和图片解码均已验证。新增浏览器回归已接入普通检查和 Pages 发布前检查；这些仍是本地验证结果，不代表已推送或发布。

### 最终构建的完整缓存基线

最终 `managed` 构建与当前修改模块逐一核对一致，使用同一份留存公开内容和用途包、实际 IndexedDB 及生产图片管理器测量。Chromium 149.0.7827.55，桌面浏览器的 375×812 视口，不模拟手机 CPU，不做网络节流；每类只有一个样本。测量在核心图片就绪后点击等价的完整准备入口，不能替代首屏、真实手机或公网测速。

| 场景 | 完整准备入口耗时 | 图片对象 | 检查峰值 | 状态通知 | 任务内最大定时器间隔 | 本页图片响应正文字节 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 首次准备完整图库 | 48,437 ms | 5,294 | 8 | 898 | 221 ms | 243,782,341 |
| 全部缓存命中 | 70,152 ms | 5,294 | 8 | 1,466 | 56 ms | 0 |
| 每 20 个缓存对象移除 1 个后恢复 | 81,552 ms | 5,294 | 8 | 1,450 | 220 ms | 199,142,309 |

图片字节是本页累计值，包含进入测量前的核心图片；耗时从完整准备入口开始。定时器间隔仅用于观察任务期间响应，不等于实际输入延迟或 P95。稀疏缺失仍按所在包恢复，不能按缺失对象比例承诺同等比例的下载量。

这组结果确认检查并发有界、暖缓存不下载以及后台完整准备期间的通知成本，但完整图库校验仍然较慢。本轮不跳过哈希、不默认检查全库，也不据此宣称全量准备或公网访问普遍提速。早先临时装配站点的计时不用于最终加载速度结论，最终基线以上表为准。

最终验证为：299 项全量 Node 测试通过，随后新增的增量订阅回归及同文件 10 项定向测试通过；14 项 Python 测试通过；四组浏览器入口验证通过，配额探针的环境限制按上文单列；Docker 构建和公开候选检查通过。

## 952db30 之后的公共资料失败恢复

并行读取资料时，一个请求失败会中止本轮，但其他已经收到正文的任务仍可能执行迟到回调。进度发布现在同时要求同一代、同一任务和本轮控制器未中止；失败终态不再退回下载或校验状态，重试入口能够恢复可用，整套验证与原子写入保持不变。

`tests/content-progress-regression.test.mjs` 覆盖 503、请求超时／中止、哈希失败和旧资料缓存复用。未修代码下，前三项复现终态被覆盖；修复后全部通过，并检查失败零写入、旧版本保留和重试成功。原有本地导入优先与成功路径回归继续保留。

`tests/browser_content_updates.py` 的真实 HTTP 服务先送完同批两个成功响应，并等待浏览器报告正文接收完成，再令另一个请求返回 503；浏览器检查错误状态、可用的重试按钮，并通过点击按钮恢复。该浏览器场景验证并发失败恢复，不将 HTTP 调度描述为与受控微任务探针完全相同的时序。

加载诊断增加 `public_content` 白名单：`phase`、`version`、`availableVersion`、`cached`、`error_code`、`bytes`、`totalBytes`。字节仍表示公开资料响应正文，未知异常只输出固定错误码，不导出异常正文、账号、请求正文或 URL。

本节描述本地源码与回归合同；具体发布以对应提交的部署任务和线上清单为准。真实浏览器配额拒绝的未验证边界不变。
