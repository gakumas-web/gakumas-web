# 模拟引擎候选池兼容性审计

[文档索引](README.md)

内容更新、映射生成或引擎升级后，先统一审计技能卡、每项附魔的全部等级和比赛 P 道具，再交付候选站点。流程仅读取公开内容，不需要账号快照、游戏凭据或网络服务。

## 日常与发布流程

1. 按现有内容安装／构建入口生成候选站点，保留内容频道与分包清单。需要修复映射时，使用 `tools/build_contest_engine.py` 的固定来源校验和映射生成入口，不能跳过定义指纹。
2. 对实际交付目录执行审计：

   ```sh
   npm run audit:engine -- --site dist --baseline-snapshot local/contest-baseline/baseline.json --baseline tools/contest-engine-compatibility-baseline.json --report local/contest-engine-audit.json
   ```

3. 检查报告中的 `candidatePoolChecked`、`newUnsupported`、`stageChecks` 和 `pendingStages`。全部技能卡、附魔与 P 道具始终完成真实审计。新舞台明确缺少参考或引擎记录时仅将模拟标为待补，允许基础资料正常发布；已就绪舞台不得降级为待补。定义变化、新增不支持项、回合或规则不一致、内容哈希错误、程序缺失及真实执行失败仍阻止发布。
4. 修复可证明等价的映射后重新审计。确实未实现的效果继续排除，并在人工核对支持范围后显式更新基准：

   ```sh
   npm run audit:engine -- --site dist --report local/contest-engine-audit.json --write-baseline tools/contest-engine-compatibility-baseline.json
   ```

基准表示已记录的限制，不表示这些条目已支持。不要为通过发布检查而无条件覆盖基准。GitHub Pages 工作流对新构建与复用制品都执行上述检查，并保存 `contest-engine-audit` 报告制品。

排查本地源码时可增加 `--program .`，复用站点中的公开资源但校验当前源码；正式发布不使用这个参数。要求零不支持项时增加 `--strict`，任何不支持项都会返回非零退出码。报告包含内容版本、分包哈希、引擎引用提交、程序与映射哈希，以及逐项 ID、名称、原因和定义指纹，可用于定位与比较。

## 浏览器运行时

界面只加载由固定来源生成的轻量能力索引；11 字段投影不依赖引擎 bundle。正常构建和引擎更新同步生成该索引，正式 Worker 与审计器再逐项核对真实 registry 和 map，索引过期或漏项仍会阻止计算。

舞台选择保留 raw 参数与规则。缺模拟参考或引擎记录时显示“模拟资料待补充”，不创建模拟、推荐或倍率计算任务，也不启动该舞台的草稿配置；首次默认选择最新可用舞台，已经选择的舞台与草稿不自动切换。赛期未知只显示未收录，不影响数值模拟。参考或引擎后补后，正式能力校验通过即可启用，无需制造空的数据更新。

自定义推荐打开时对当前账号、舞台对应的候选池执行同一套正式 Worker 校验，完成前禁止开始搜索。不支持的技能版本、附魔项目与 P 道具不再作为可选候选，支持／排除计数和清单仅供内部检查，不显示在配置界面。

已经固定的不支持配置保留在表单中并明确提示，不静默替换或丢弃。搜索提交后再次校验固定技能、附魔、P 道具和公共卡组，失败发生在评分前；自动候选继续按支持结果过滤。审计只证明定义和映射的支持情况，不代替回忆评级、持有解锁、容量和附魔组合合法性校验，也不保证推荐分数最优。

引擎署名直接读取生成映射的来源提交，并链接到对应提交，不另行维护可能漂移的版本文字。

## 配套引擎自动更新

Pages 在构建或复用制品前冻结当时已部署的 release、内容清单、原始 progression/effects、旧目录投影和引擎/map，验证各自哈希并在捕获结束时重新核对版本。`update` 与最终审计共用同一份 `--baseline-snapshot`，不得用当前候选反算旧能力；网络、混装或校验错误不能退化为空基线。只有显式首次部署且程序与频道均真实 404 时才允许空基线。

公共资料同步工作流同时检查 GakumasTools 引擎版本。即使内容版本未变，只要引擎运行输入发生变化，也会触发 Pages 构建。检测时固定提交与核对报告，构建时读取同一份 `engine-update.json`；不在下载与打包之间跟随可变的 HEAD。

`tools/update_contest_engine.py` 将固定来源中的新增记录、已有记录修正、附魔数据、引擎代码及运行文件集合变化统一选为 `candidate`，记录新增、修改、删除的文件，并固定所选提交与文件哈希。该状态只表示待验证，不代表构建或兼容性检查已经通过。只变更说明或 CSV 且运行输入未变时为 `unchanged`。舞台参考仍由数据项目的 `data/reference/contest-stages.json` 交付，不能用引擎更新掩盖内容缺失。

技能卡、P 道具、P 偶像和舞台记录仍须为数组，记录 ID 必须是唯一的整数；允许正常修正、重排和增删，但拒绝重复 ID 或错误结构。来源 `LICENSE` 变化也会停止，避免新来源沿用未经更新的许可声明。

候选在隔离目录生成，使用工作流固定的 esbuild 版本；人工身份映射按下述固定身份锚点核验，不能无条件覆盖两侧指纹。内容效果版本变化时，先对照内容所固定的原始公开表，逐项核验已有持续效果、触发条件、搜索条件和效果定义，再推进持续效果补充证据的来源元数据。已登记的持续效果证据发生变化仍停止；人工身份映射中的公开说明、数值或上游实现修正可以进入候选回归和完整审计。

生成后运行实际引擎回归及当前内容的完整审计，全部通过后才把生成结果应用到构建工作区并重建站点。失败保留原程序和线上频道，不自动更新兼容性基准，也不把旧引擎与未通过审计的新资料一起发布。下一轮核验已部署引擎的真实上游快照和全部哈希后，以该版本作为基线；不再要求它相对程序仓库固定版仅包含追加记录。

自动更新不直接提交或推送程序仓库。站点的 `content/engine-source.json` 保存本次引擎固定提交与全部输入哈希；`engine-update` 制品保留核对计划、生成报告、审计结果、来源锁及映射证据。程序源码提交与引擎上游提交分别记录，可独立追溯。

本地只准备候选：

```sh
python3 -B tools/update_contest_engine.py --site local/ui-visual-refinement/dist \
  --baseline-snapshot local/contest-baseline/baseline.json \
  --esbuild <固定版本的esbuild路径> --output local/engine-update-candidate
```

增加 `--apply` 才将已通过全部验证的候选写入本项目；这不提交 Git，也不部署站点。输出目录已经包含候选时应另用新目录，保留失败依据。构建、回归或审计失败时，`report.json` 记录失败阶段、退出码和固定计划；构建身份冲突还会在 `build.json` 记录键、匹配到的 ID 及当前／人工登记的双侧指纹。再次使用已有候选目录会拒绝执行，保留首轮报告。

## 名称匹配边界

映射先采用原名称；找不到时，统一全角／半角、空白、标点和常用装饰符号。强化版本可忽略末尾展示加号，但仍按独立强化字段、计划类型和来源区分，并检查卡片结构或道具类别。归一化后存在多个候选时拒绝匹配；汉字、假名、数字和长音保留，不使用模糊相似度替代身份。能够解释的效果发生冲突时仍拒绝；映射后的公开定义继续接受完整指纹校验。

使用条件与效果触发条件的附魔分别匹配，触发原文参加指纹。姿态阶段附魔同时检查原效果、目标效果和卡片已有姿态动作，避免引擎的整卡成长机制误改另一种姿态。自动规则无法证明对应关系的条目保持排除，人工核对的上游身份映射按下一节处理。

## 固定上游身份对应

模拟行为以 `tools/contest-engine-source.json` 锁定的上游版本为准，不在本项目修正上游数值、动作或附魔补丁。名称存在汉字／假名差异、上游错字或复杂附魔尚无自动翻译时，可在 `tools/contest-engine-reviewed-mappings.json` 登记经人工核对的对应身份。每项包含公开定义指纹、上游定义指纹和核对说明；这证明身份已确认，不承诺两边效果完全等价。已知数值或实现差异也在该文件说明，并原样沿用上游。

生成器检查固定版本、双向指纹、卡片结构、道具强化状态及计划，以及附魔适用卡片和等级。每条已核对身份的 `identity` 固定两侧的身份锚点，`identityEvidence` 保存建立锚点时已验证的原始双侧指纹、内容版本和引擎提交。建立锚点必须先用原始公开定义和固定引擎来源重建这两个指纹，不能从已变化的候选反推人工证据；锚点及原始证据不自动改写。

身份合同按对象区分：

- 技能卡固定公开 ID、强化等级、计划、稀有度、类别及偶像／支援／角色来源；上游固定 ID、强化状态、计划、稀有度、类型、来源类型及所属 P 偶像。
- P 道具固定公开 ID、强化状态、计划、稀有度及偶像／支援来源；上游固定 ID、强化状态、计划、稀有度、模式、来源类型及所属 P 偶像。
- 附魔固定每一级的公开 ID 和等级，以及上游 ID、类型、等级上限和已有 alias；仍检查当前适用卡片和等级一致，不自动扩大等级身份。

固定来源中的名称、说明、费用、数值、动作、效果或价格发生修正时，只要两侧身份锚点不变，名称匹配不存在歧义或其它 ID 冲突，且正式结构检查通过，就可在隔离候选中推进当前双侧定义指纹。`reviewedMappingResolutions` 以 `reviewed_identity_preserved` 记录规则、原始证据、当前身份和旧／新指纹，报告的 `source` 固定本次提交与公开内容身份。身份锚点变化、目标缺失、换 ID、名称歧义或结构／适用卡片不一致仍阻断；没有固定锚点的旧记录也不推测放行。候选必须继续通过实际引擎回归、完整候选池审计和既有可用舞台保护，才可由更新入口整体应用，不能自动刷新不支持基准。

名称修正另有更窄的证明分支：公开定义仍命中原始指纹，当前名称匹配唯一且仍指向原 ID，新上游名称与公开名称归一化后完全一致。`engineName` 保存固定旧名称；把候选名称还原后，整个上游记录必须重建原始 `engineSha256`。这时无需推进原始指纹，报告以 `engine_name_aligned` 记录旧／新名称及指纹；此分支不扩展到附魔定义。

生成映射的来源元数据记录身份清单哈希，审计仍检查实际站点的映射和引擎文件。`--mapping-only` 仅生成映射，不重建或修改引擎包。站点更新与数据候选审计共用此生成器和身份合同。

固定回归样本保留，普通 CI 继续按固定公开定义运行。隔离候选回归显式设置 `GAKUMAS_CONTEST_TEST_EFFECTS`，先核对当前 effects 的完整文件哈希和版本与生成映射一致，再通过正式目录及 `contestSimulationReference` 按原 ID、强化和附魔等级重建测试输入。测试的预期引擎 ID、真实 `StageEngine` 执行、直接上游对比及篡改拒绝断言保持不变；找不到原身份、等级或依赖直接失败，旧定义也不能冒充当前定义通过。这样同身份公开定义修正无需继续接受旧指纹，当前内容仍由完整候选池审计独立核验。

## 数据候选的独立审计入口

`tools/audit_contest_candidate.py` 接收数据项目导出的候选与基线五个业务分包及 `review-manifest.json`，校验内容哈希后，以指定的引擎提交生成程序并运行完整候选池审计。目标包含最新赛季所有舞台、新增或定义变化的舞台；舞台定义包含递归解析的隐藏物品和效果等依赖，因此依赖变化也会纳入受影响的历史舞台。目标还包括新近可用舞台与固定基线最近可用赛季的完整保护范围。删除舞台、未知或新增不支持机制均不能当作通过；明确缺输入的新舞台保留为待补，不阻止基础资料发布。

数据侧通过固定的公开 Web 提交调用该入口，参数为 `--candidate-content`、`--baseline-content`、`--engine-commit`、`--auditor-commit`、`--esbuild` 和 `--output`，均为必填；输出目录须不存在且不能与输入重叠。报告 `contest-engine-audit-report.json` 记录输入清单哈希、审计器代码身份、引擎锁、支持范围基准和逐舞台结果；`passed` 与 `partial` 退出码均为 `0`；`waiting` 为 `2`，`blocked` 为 `1`。`partial` 必须完整检查候选池，执行舞台与待补舞台无交集且精确覆盖全部目标；报告绑定基线程序的锁、registry 与映射身份。只有明确缺少参考或引擎记录能标为待补，日期缺失独立显示为未收录。

报告的 `auditedRecords` 只列实际校验通过的候选所引用的公开根记录，附魔等级对应的原卡去重后记录一次。每项包含 `table`（`ProduceCard`／`ProduceItem`）、`id`、仅卡片具有的 `upgradeCount`，以及 `fingerprint`。指纹来自本次输入表中对应完整投影行的递归键排序、无空白 UTF-8 JSON 的 SHA-256；不对候选装配对象求哈希，不把隐藏、排除、不支持或未引用效果标为已审计。外层报告原样传递此列表并用整体报告指纹绑定；消费方核对格式、复合主键、无重复及本次公开行哈希后，才可把它作为放宽规则的证据。旧报告缺少该字段时仍走原有严格规则。

本地工作树审计身份为 `local_validation` 时，仅供验证，不能满足数据自动合并所需的 `verified_commit`。提交身份核验使用 Git 2.39 可用参数，保留 `GIT_NO_LAZY_FETCH=1`、禁止交互、根路径核对、逐文件哈希及超时限制；工具版本不支持某个新参数不能成为误降本地验证身份的原因。

启用数据侧自动流程前，应先将此审计入口及其依赖提交到可匿名读取的 Web `main`，再提交并启用数据侧配置。这里描述源码能力，不表示远程流程或站点已经发布。
